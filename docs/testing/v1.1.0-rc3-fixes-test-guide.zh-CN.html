1. 测试准备与升级方式

  • 测试包：从 Actions 运行 #36538306353 下载产物 neoruntime-hailo-firmware-v1.1.0-rc3.tar.gz。
  • 升级入口：Web 控制台 → 设置 → 设备信息 → 固件升级，上传 .tar.gz 包。
  • 建议设备：192.168.93.72（慢 eMMC 板，OTA 提速的基准机型）与 192.168.93.214（旋转 / IR 问题复现机型），其余项目任意 rc2 设备均可。
  • 升级计时：从点击「确认升级」到设备重新上线，请记录总时长（对比数据：rc2 在 93.72 上为 11 分钟 06 秒）。
重要：升级期间（页面显示写入/重启中、或页面短暂失联时）不要断电、不要手动重启设备。 本批修复消除了"升级太慢导致误判失败"的主因，但"升级被强行中断后 OTA 状态卡死"的自愈修复不在本批范围内， 中途重启仍会造成设备无法再次升级（需要人工恢复）。请等升级流程自然结束。

3. 逐项修复详情与验证步骤

#1 固件升级（OTA）大幅提速 P0 perf(deploy)

旧版本现象

rc2 在慢 eMMC 设备（93.72）上，固件升级全程需要 11 分钟以上，而前端轮询 10 分钟就超时报 「升级失败 / 设备未上线」——实际升级还在正常进行，属于假失败。更糟的是用户看到"失败"后手动重启设备， 会把升级流程拦腰打断，之后设备的 OTA 状态卡在"正在升级"，所有后续升级都被拒绝（93.72 曾两次需要人工恢复）。

修复内容

升级部署过程中的"备份当前版本"和"预置新版本"阶段原先要把约 300MB 的程序文件反复整份复制（合计写入超过 1GB）。 现在这些不可变目录改用硬链接（零数据拷贝），部署写入量从约 1.3GB 降到约 300MB， 预期升级全程从 11 分钟降到 3~5 分钟，回到前端等待窗口之内，不再出现假失败。

验证步骤

  1. 在 93.72（rc2）上通过 Web 控制台上传 rc3 包，勾选确认，点击「确认升级」，开始计时。
  2. 观察全程：预期 3~5 分钟内完成（含自动重启），前端显示升级完成并跳转登录页，不再出现"设备未上线"超时提示。
  3. 重新登录后进入 设备信息 页，确认固件版本为 v1.1.0-rc3。
  4. （可选）读取部署日志确认硬链接生效：文件 /data/aipc-data/ota-work/current/deploy.log 中应出现一行 Package trees hardlinked onto /data (same filesystem, no data copy)。
  5. 升级完成后查看 存储 页：/data 分区剩余空间应与升级前基本持平（旧版每次升级要临时多占约 800MB）。
配套验证（P1，#11）：回滚功能保持可用——若升级了不合适的包，使用 deploy.sh rollback（或制造一次健康检查失败触发自动回滚）确认能正常回退到旧版本、服务恢复正常。此项建议由开发配合执行。

#2 旋转画面后图像模式丢失（IR 紫图） P0 fix(hailo15)

旧版本现象

旋转画面（90°/180°/270°）会触发图像管线整体重建，重建后管线回落到默认图像模式而不再是用户设置的模式。 最严重的是 IR 夜视模式：重建后跑的是彩色管线、但 IR-Cut 已移除、红外补光开启，画面呈现紫色 （2026-09-29 在 93.214 实机复现）。其他非默认模式（如灰度）旋转后也会被悄悄切回默认。

修复内容

旋转重建时先记住当前生效的图像模式，重建完成后、管线启动前恢复该模式；若恢复失败（例如该模式当前被温控门控限制）， 则回退到默认模式，但旋转操作本身不会失败。

验证步骤

  1. 设备切到 IR 夜视模式，确认画面为正常黑白 IR 效果。
  2. 在 设置 → 图像 中把旋转依次改为 90°、180°、270°、0°，每次保存后等预览刷新。
  3. 预期：画面始终为正常 IR 黑白，不出现紫色；模式指示仍为 IR。
  4. 换灰度等其他非默认模式重复上述旋转操作，预期模式保持、效果正确。
  5. 旋转后用主码流拉流（RTSP/网页预览）确认旋转方向正确、宽高对调符合预期。

#3 删除的码流不再"复活" P1 fix(platform-api)

旧版本现象

删除一个码流（如 sub 子码流）后，媒体状态页 / 配置里的编码器列表中它又出现回来—— 状态与配置"记得"已删除的流，编码输出也可能残留，造成列表与实际不符。

修复内容

编码器列表改为以设备实际生效的码流集合为准整体重建（更新、新增、删除都同步），删除的流在状态、配置、编码输出三处都彻底消失。

验证步骤

  1. 初始两路码流（main + sub）。删除 sub 码流。
  2. 刷新媒体状态页 / 码流配置页：预期 sub 彻底消失，编码器列表只剩 main。
  3. 重新添加 sub，再删除；反复增删 2~3 轮，列表始终与实际一致。
  4. 删除后尝试用旧的 sub 拉流地址取流，预期无流输出。

#4 快速增删改码流不再楔死；非法请求明确报错 P1 fix(camera-daemon)

旧版本现象

  • 楔死：快速/并发地对 sub、third 码流执行 开启/关闭/编辑 时，可能出现子码流进入 「配置显示已启用、实际永远打不开」的状态，只能重启设备恢复。
  • 静默错配：重配置请求里出现非规范或重复的码流 ID 时，旧版不报错，而是按位置错误对应， 可能把 A 流的参数设到 B 流上。
  • 重启后配对错乱：经历过"删除再添加"后设备重启，sub 流可能拿到 third 流的分辨率（反之亦然）。

修复内容

所有码流增删改操作串行化（杜绝并发插队）；重配置载荷先校验再执行，非法 ID 直接拒绝并报错； 重启时按固定规范顺序（main/sub/third）配对；配置与实际状态不一致时自动走恢复路径而不是拒绝服务。

验证步骤

  1. 快速连续操作：开启 sub → 编辑 sub 分辨率 → 关闭 sub → 再开启，中间几乎不等待；重复 3~5 轮。
  2. 预期：每次操作后码流状态与配置一致，最终 sub 能正常开启出流，无卡死。
  3. 对 sub 和 third 交替做"删一个、加一个"，然后重启设备。
  4. 重启后分别拉 main / sub / third 流：预期每路分辨率与其配置一致（sub 不会拿到 third 的分辨率）。
  5. （可选，需接口工具）发送带重复流 ID 的重配置请求，预期收到明确报错而非静默接受。

#5 媒体管线五项加固 P1 fix(hal)

旧版本现象（五类）

  • 并发压力崩溃：对码流高频做删除 + 重配置的组合压力时，程序可能直接崩溃退出。
  • 竖屏尺寸漂移：旋转 90°（竖屏）时，实际编码输出的宽高与设置值对不上（请求与实际 SPS 不一致）。
  • 参数改不动：连续多次修改分辨率/编码参数后，可能出现"改了但没生效"（内部临时配置文件名超长后复用了旧配置）。
  • 运行中改参数崩溃：管线运行中轻量修改参数存在一个约 39ms 的竞态窗口，现场设备曾因此 core dump。
  • 新增码流码率错误：新添加的子码流会继承主码流的码率/GOP（如 8Mbps / GOP 30），而不是自己设定的值。

验证步骤（按日常可操作性排序）

  1. 码率验证：添加 sub 码流并设定码率（如 1Mbps）、GOP（如 30 之外的自定义值），拉流用码率分析工具（ffprobe / 播放器统计）检查实际码率与设定一致，不再是主码流的 8Mbps。
  2. 竖屏尺寸：旋转 90° 后拉流检查实际输出宽高（如 3840×2160 应变 2160×3840），与设置页显示一致。
  3. 连续改参：连续 5 次以上修改主码流分辨率/码帧组合，每次等生效，预期每次都真正生效（画面清晰度/码率可见变化，无"原地不动"）。
  4. 压力测试：对 sub/third 做 2~3 分钟的快速增删改混合操作，预期设备不重启、不崩溃、结束后码流状态正常。

#6 SD 卡格式化期间：页面锁定 + 磁盘监控不卡死 P1 feat(web) + fix(platform-api)

旧版本现象

  • 格式化大容量 SD 卡（如 256GB）耗时数分钟，期间页面可以随意点击跳转，中途离开可能造成状态不一致。
  • 格式化进行时，磁盘监控接口会被格式化写入阻塞，卡住超过 30 秒，前端存储页转圈超时。

修复内容

格式化进行中前端全屏锁定：屏蔽所有界面操作、阻止页面内跳转（包括浏览器后退）、关闭/刷新标签页时弹出确认； 格式化结束后自动解锁。后端磁盘探测加 3 秒上限，超时后降级为只报告已挂载分区，不再长时间挂起。

验证步骤

  1. 插入大容量 SD 卡，在 设置 → 存储 中发起格式化。
  2. 格式化期间依次尝试：点击左侧菜单跳转、浏览器后退按钮、关闭标签页——预期全部被拦截或弹出确认提示，页面显示格式化进行中的锁定遮罩。
  3. 格式化期间另开一个标签页打开 存储/监控 页面：预期几秒内能打开（磁盘信息可能只显示已挂载分区，属于预期的降级表现），不再转圈 30 秒。
  4. 格式化完成后：锁定遮罩自动消失，可以正常跳转；磁盘信息恢复完整显示。

#7 应用导入：参数校验 + 应用身份保持 P1 fix(web) + fix(platform-api)

旧版本现象

  • 导入应用时填写的非法参数（如 app id 含特殊字符、CPU 配额为 0 或负数、内存值非法、模型别名重复等）没有即时提示，直到安装阶段才以模糊错误失败，甚至带病安装。
  • 导入 .neoapp 应用包时，应用自身的身份信息（名称/版本等）可能被导入流程覆盖改写。

修复内容

前端在导入流程中对每个字段做即时校验（红字标出具体问题）；应用包身份字段保持原值不被覆盖；后端上传接口同步增加同样的拦截（双重保险）。

验证步骤

  1. 导入应用时在应用 ID 中输入 非法字符! 、CPU 配额填 0 或 -1、内存填 0 等：预期对应字段立即出现红色错误提示，无法继续下一步。
  2. 改正为合法值后流程正常继续、安装成功。
  3. 导入一个正常的 .neoapp 包：安装后应用的名称、版本与包内声明完全一致，未被改写。
  4. （可选，需接口工具）绕过前端直接调上传接口提交非法 manifest，预期后端同样拒绝。

#8 应用导入：权限区隐藏"设备控制"选项 P2 fix(web)

旧版本现象

应用导入向导的权限配置区显示"设备控制"类权限（灯光 light、IR-Cut、云台 PTZ、镜头 lens），这些权限项不适用于应用导入场景，勾选后没有意义。

验证步骤

  1. 打开应用导入向导，进入权限配置步骤。
  2. 预期：不再出现 灯光 / IR-Cut / 云台 / 镜头 四个设备控制项；其余权限项（如摄像头、模型访问等）显示与勾选正常。

#9 安装向导：CPU / 内存非法值明确拒绝 P2 fix(app-manager)

旧版本现象

应用安装向导中 CPU（如 0、-1、非法百分比）或内存（0、负数、超大值）填写非法时， 后端报的是笼统的"服务错误"，难以为用户定位问题。

修复内容

后端对向导可编辑的 CPU / 内存字段做严格校验，非法值返回「应用配置无效（Invalid app configuration）+ 具体字段原因」，错误类型也从"服务错误"修正为"请求参数错误"。

验证步骤

  1. 在安装向导中把 CPU 填 0 或 -1、内存填 0，提交。
  2. 预期：收到"应用配置无效"类提示并指出具体字段，而不是"服务错误"；填合法值后正常生成与安装。

#10 程序崩溃时报告更可靠（底层改进） P2 fix(hal)

修复内容

崩溃信号处理器多项加固：栈溢出类崩溃也能生成报告（独立信号栈）、避免报告过程中死锁、报告头部信息（崩溃地址、线程名等）先行落盘。 这是可维护性改进：现场设备出问题时能留下可分析的崩溃日志（/data/core/ 与崩溃日志）。

测试建议

常规功能测试中无需专门构造崩溃；正常测试过程若不幸遇到崩溃，请保留设备现场并导出 /data/core/ 目录与系统日志提供给开发——本修复正是为了让这些报告更完整。

4. 十分钟冒烟清单

时间紧张时，至少完成以下最小集（覆盖两个 P0 与最高频的 P1）：

  • rc2 → rc3 升级成功且计时 ≤ 5 分钟，前端全程无"升级失败/设备未上线"假提示（#1）
  • 升级后版本号为 v1.1.0-rc3，各服务状态正常，预览/拉流正常
  • IR 模式下旋转 90°/180°/270° 不出现紫图，模式保持（#2）
  • 删除 sub 码流后列表不再显示、拉流无输出；重新添加可正常出流（#3）
  • 快速开关 sub 码流 5 轮无卡死，最终状态正确（#4）
  • 新增 sub 码流码率与设定值一致，不是主码流的 8Mbps（#5）
  • SD 卡格式化期间页面锁定、后退/关闭被拦截，另一标签页存储页不卡死（#6）
  • 应用导入填非法 app id / CPU 0 → 字段即时红字报错（#7）

附录 C：YAML 配置文档清单

本批修复涉及应用导入校验（#7/#8/#9）与升级部署校验，测试时会接触到以下配置文件。 分三类：应用侧（测试人员直接编写/导入）、设备服务侧（固件包内置，升级时部署并校验）、 包级兼容清单（注意是 JSON 格式）。

C.1 应用侧：app.yaml（应用清单）

每个 AI 应用一份，随 .neoapp 包导入，或由「应用安装向导」生成； 设备上存放于 /data/aipc/apps/manifests/<应用ID>/app.yaml。 仓库字段定义：platform/app-manager/manifest/manifest.go。本批校验相关的字段以 对应修复 标注：

字段示例值说明 / 校验要点本批相关
metadata.idsmoke-detector应用 ID，仅允许字母数字开头，含 .-_；非法字符导入时字段即时红字报错#7
metadata.name / version烟感检测 / 1.2.0应用身份信息；导入 .neoapp 时保持包内原值，不被向导覆盖#7
spec.resources.cpu"50%" 或 "0.5"CPU 配额；必须大于 0，百分比/小数非法值在向导与后端双重拒绝#9
spec.resources.memory"256Mi" / "1Gi"内存上限；必须大于 0 且为合法容量单位，0 / 负数 / 超大值被拒#9
spec.permissions.*video / inference / events / network应用权限；向导中正常展示与勾选—
spec.permissions.devicelight / ir_cut / ptz / lens设备控制权限：YAML 中保留以兼容，但向导权限区不再展示（见 #8）#8
spec.models别名 → 模型映射含模型 id / path / required；模型别名重复在导入时被拒#7
spec.env[].nameAIPC_MODEL_DET环境变量名须以字母/下划线开头（字母数字下划线），非法即报错#7
spec.image / volumes / autostart / restart_policy / healthcheck …—容器镜像、挂载、开机自启、重启策略、健康检查等常规字段，本批未改动—

C.2 设备服务侧：固件包内置服务配置（configs/ → 设备 /data/aipc/etc/）

升级部署时会把这些 YAML 从包内部署到设备 /data/aipc/etc/，且部署预置校验 （validate_staging）要求核心文件必须存在且非空——缺任何一个，升级会在校验阶段失败并自动回滚。

文件（仓库路径 configs/…）用途与本批修复的关联
platform/camera-daemon.yaml相机与码流配置（流列表、分辨率、编码）#2 旋转模式、#3/#4 码流增删改、#5 管线加固
ai/ai-runtime.yamlAI 运行时配置（模型加载、推理服务）—
platform-api.yaml（仓库根 configs/）平台 API 后端配置#3 编码器列表、#6 磁盘监控接口
platform/app-manager.yaml应用管理服务配置#7/#9 应用导入与向导校验
platform/event-bus.yaml事件总线配置—
platform/device-control.yaml、platform/discovery.yaml、platform/onvif.yaml设备控制 / 设备发现 / ONVIF 配置—
product.yaml（随包部署）产品标识信息升级校验必备项之一
preload.yaml、system/sysctl.d/（内核看门狗 sysctl）预加载与内核自愈参数随包部署，一般不涉及测试操作
测试注意：升级部署会以包内配置覆盖设备上的服务 YAML（配置部署开关开启时）。 如需自定义服务配置，请通过 Web 控制台修改（走配置管理留痕），不要手工改 /data/aipc/etc/ 下的文件——手工改动会在下次升级时被覆盖，且可能与"配置已改但升级后又复原"的表象混淆。

C.3 包级兼容清单：app-manifest.json（JSON 格式，非 YAML）

固件包内的兼容性声明，位于包的 opt/aipc/app-manifest.json，字段定义见 platform/osupgrade/compatibility.go：

字段作用
min_os_version / max_os_version应用包支持的 OS 版本闭区间；上传固件包时若当前 OS 不在区间内，前端直接提示「应用包与当前系统不兼容」并给出当前 OS 与支持范围（本次 93.72 升级实测：OS 1.12.0，范围 1.12.0-1.12.0）
target_data_schema包期望的数据结构版本；与设备持久化的 schema 不一致时同样判定不兼容
排查提示：升级/导入报「不兼容」类错误时，先核对 app-manifest.json 的 OS 区间与设备当前 OS 版本 （设备信息页可查），再看 schema 版本——这两处是判定数据源，与 app.yaml 内容无关。
